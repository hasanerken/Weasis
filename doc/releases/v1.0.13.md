# v1.0.13 — Post Mortem Analysis

**Release Date:** 2026-03-09
**Type:** Bug Fix + Feature

---

## Why We Released

ZenViewer v1.0.12 was completely non-functional on Intel (x86_64) Macs. The app silently failed to launch with no error shown to the user. Additionally, a frequently requested feature — disabling the automatic 1x2 dual series layout — was added in this release.

---

## Problems

### 1. ZenViewer Failed to Launch on Intel Mac — "Failed to Launch JVM"

This was the most severe bug in ZenViewer's history. The Intel DMG installed without error but the app never opened. The failure manifested as a native macOS crash with the message:

```
Failed to launch JVM
Library not loaded: /usr/local/opt/harfbuzz/lib/libharfbuzz.0.dylib
class file version 68.0
```

The root cause was a chain of three compounding issues:

---

#### Root Cause A: Wrong JDK Used for x64 Build (Homebrew openjdk 25)

The x64 DMG was built using the Homebrew-installed `openjdk 25` JDK. When `jpackage` bundles an app, it copies the JRE from the build JDK into the `.app` bundle. Homebrew's `libfontmanager.dylib` (part of the JDK) links against Homebrew's `harfbuzz` library (`/usr/local/opt/harfbuzz/lib/libharfbuzz.0.dylib`). This library is present on the build machine (developer Mac with Homebrew) but **not on end-user machines**. The JVM therefore failed to initialize the font subsystem on launch.

Additionally, Homebrew openjdk 25 requires **macOS 11.0+**, but many Intel Macs in clinical environments still run macOS 10.14 or 10.15.

**Fix attempt 1:** Switch to Temurin JDK 21 — a self-contained distribution with no external dylib dependencies, supporting macOS 10.12+.

---

#### Root Cause B: Bytecode Version Mismatch (class file version 68.0)

After switching to Temurin 21 for the x64 bundle, a second error appeared: `class file version 68.0`. Class file version 68 = Java 24. The Maven build was compiling with `java-version=24` (set in `weasis-parent/pom.xml`), producing bytecode that the bundled JRE 21 (class file version 65) could not load.

**Fix attempt 2:** Downgrade `java-version` in `pom.xml` from 24 → 21 so the compiled bytecode matches the bundled JRE.

---

#### Root Cause C: Upstream Code Requires Java 22+ (unnamed variables)

Downgrading to Java 21 bytecode target caused a compilation failure:

```
error: unnamed variables not supported in -source 21
```

Upstream Weasis uses Java 22's unnamed variable feature (`_`) in pattern matching expressions. This is a language feature, not a library feature — the source code cannot compile below Java 22 without modifying upstream code.

**Final Fix:**
- Switch to **Temurin JDK 22 x64** (`/tmp/jdk22-x64`) for the x64 DMG bundle — self-contained, no Homebrew deps, supports macOS 10.12+
- Set `java-version=22` and `jdk-version=22` in `weasis-parent/pom.xml` — bytecode version 66 matches JRE 22 exactly
- ARM64 build was unaffected (uses ARM-native JDK 25 which has no external dylib dependencies on macOS)

**Files Changed:**
- `build-dmg.sh` — switched `JDK_X64` from Homebrew openjdk 25 → Temurin 22 at `/tmp/jdk22-x64`
- `weasis-parent/pom.xml` — `java-version` and `jdk-version` 24 → 22

---

### 2. `./build-dmg.sh all` Destroyed Previously Built DMGs

**Symptom:** Running `./release.sh` (which internally called `./build-dmg.sh all`) only produced one DMG even though two architectures were built.

**Root Cause:** Each architecture run of `build-dmg.sh` starts with `mvn clean`, which deletes `target/`. Running `all` built arm64, then immediately wiped `target/` when starting x64, losing the arm64 DMG.

**Fix:** Rewrote `release.sh` to build each architecture sequentially and upload to MinIO **immediately** after each build, before the next `mvn clean` runs.

**Files Changed:**
- `release.sh`

---

### 3. Feature: 1x2 Dual Layout Toggle in Preferences

Added a user preference (`zenviewer.dual.series.layout`) to enable/disable the automatic side-by-side display of two series when opening a patient. Accessible via Preferences → ZenPACS Kısayol Tuşları.

**Files Changed:**
- `PluginOpeningStrategy.java` — read preference before collecting 2nd series
- `ZenShortcutsPrefView.java` — added checkbox UI
- `weasis-launcher/conf/base.json` — registered preference with default `true`

## Lessons Learnt

1. **Always use a self-contained, portable JDK for bundling.** Homebrew JDKs link against Homebrew libraries that are not present on end-user machines. Use Eclipse Temurin or similar distributions that are fully self-contained. This applies to both macOS architectures and Windows.

2. **Bundled JRE version must exactly match compiled bytecode version.** If `java-version=24` in pom.xml, the bundled JRE must be version 24. A mismatch results in `UnsupportedClassVersionError` at startup with no UI feedback to the user. Always verify: compile target = JRE version = bundled JDK version.

3. **Upstream language feature constraints propagate downward.** Before selecting a JDK version floor, audit upstream code for language features. Weasis uses Java 22 unnamed variables — the minimum compile target is therefore Java 22 regardless of what we prefer.

4. **Test on the actual minimum supported OS.** The Homebrew JDK issue would have been caught immediately if tested on a macOS 10.14 or 10.15 Intel machine. Do not assume developer machine behavior reflects field conditions.

5. **Build scripts that share an output directory need sequential-with-upload logic.** Any build that runs `mvn clean` mid-process will destroy other artifacts. Release scripts must upload immediately after each build step.

6. **Silent launch failures are the worst kind.** The app showed no error dialog — it simply did not open. Add crash reporting or at minimum instruct users how to find macOS crash reports (`~/Library/Logs/DiagnosticReports/`) so failures can be diagnosed quickly.
