# v1.0.14 — Post Mortem Analysis

**Release Date:** 2026-03-09
**Type:** Bug Fix

---

## Why We Released

Two user-facing bugs were discovered after v1.0.13 was deployed:

1. The 1x2 dual series layout preference was not respected for 2nd and 3rd patient openings — only the first patient honored the setting.
2. The "Ses Kaydı" (audio recording) button was overlapping the Windows minimize button and its label was truncated.

---

## Problems

### 1. Dual Layout Preference Not Applied to Subsequent Patients

**Symptom:** User disables the 1x2 layout preference in Settings. The first patient opens correctly as 1x1. However, every subsequent patient still opens as 1x2.

**Root Cause:** The dual layout logic existed in two separate code paths:
- `PluginOpeningStrategy.openViewerPlugin()` — used when a DICOM study is loaded from network/file (wado, local import). This path was correctly updated with the preference check in v1.0.13.
- `DicomExplorer.java` (around line 1089) — used when the user clicks on a patient thumbnail in the explorer panel. This second path had its own copy of the "collect up to 2 series" logic with **no preference check**. It always collected 2 series unconditionally.

When a patient is loaded for the first time (e.g. from a worklist), `PluginOpeningStrategy` opens it. When the user then navigates to the next patient by clicking in the explorer, `DicomExplorer` opens it — bypassing the fix entirely.

**Fix:** Added the same `getBooleanProperty("zenviewer.dual.series.layout", true)` preference check to the `DicomExplorer` patient click handler, wrapping the series collection loop identically to the existing fix in `PluginOpeningStrategy`.

**Files Changed:**
- `weasis-dicom/weasis-dicom-explorer/src/main/java/org/weasis/dicom/explorer/DicomExplorer.java`

---

### 2. Preference Not Persisted to Disk

**Symptom:** The dual layout preference was saved in-memory when Apply was clicked, but lost on app restart.

**Root Cause:** `ZenShortcutsPrefView.closeAdditionalWindow()` called `systemPreferences.put(...)` to update the in-memory `WProperties` object, but never called `UICore.saveSystemPreferences()` to flush it to the `weasis.properties` file on disk.

**Fix:** Added `GuiUtils.getUICore().saveSystemPreferences()` immediately after the `put()` call in `closeAdditionalWindow()`.

**Files Changed:**
- `weasis-dicom/weasis-dicom-explorer/src/main/java/org/weasis/dicom/explorer/pref/ZenShortcutsPrefView.java`

---

### 3. Ses Kaydı Button Overlapping Minimize Button on Windows

**Symptom:** On Windows, the "Ses Kaydı" floating button appeared over the window minimize button in the title bar area. The button label was also truncated.

**Root Cause:** The button width was 80px (too narrow for the Turkish label) and the right margin offset was also hardcoded to 80px, placing it too close to the native window controls.

**Fix:**
- Increased `COLLAPSED_W` from `80` to `100` to give the label room.
- Introduced `RIGHT_OFFSET = 100` constant and used it in `repositionInParent()` instead of the hardcoded `80`, shifting the button 20px further left.

**Files Changed:**
- `weasis-dicom/weasis-dicom-explorer/src/main/java/org/weasis/dicom/explorer/AudioRecorderPanel.java`

---

## Lessons Learnt

1. **Duplicate logic is a maintenance hazard.** The "collect 2 series" logic was copy-pasted into two places (`PluginOpeningStrategy` and `DicomExplorer`). When a preference was added to control it, only one location was updated. Consider extracting shared logic into a single utility method to avoid this class of bug.

2. **In-memory preference updates must be explicitly flushed.** Weasis's `WProperties` / `systemPreferences` object is in-memory only. Calling `put()` does not write to disk — `saveSystemPreferences()` must be called explicitly. Always pair preference writes with a save call.

3. **Platform-specific UI sizing needs platform testing.** The button dimensions were tuned on macOS and broke on Windows where native window chrome (title bar buttons) occupies different screen real estate. UI elements near window edges should be tested on all target platforms.

4. **Test all navigation paths, not just the primary load path.** The bug only manifested when navigating to a patient via the explorer thumbnail click — a different code path than the wado/file load path. Integration testing should cover both entry points.
